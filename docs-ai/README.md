# docs-ai — 计划、行动与修订

本目录记录实质的适配器工作：写代码前的计划、完成后的行动记录、后续修订，以及只有后续条目确实需要时才增加的活 runbook。它不只回答「为什么」。它不是工作笔记，也不是能力合同。

文档用中文写。协议名、命令、路径和代码标识保持原文。

能力与发布边界留在 `README.md`、`COMPATIBILITY.md`、`TESTING.md`、`RELEASE.md`、`MIGRATION.md`。常驻适配器边界留在 `AGENTS.md`。不要把那些边界抄进每一个条目。

本 README 不计入编号。当前尚无编号条目。不要回填已有实现。

下面的模板是唯一一份。`.omp/skills/write-ai-doc/SKILL.md` 是指向这里的触发器。不要在 skill 里再放一套模板，也不要把 skill 复制到别的 agent 技能目录。

## 何时写

只有当工作必须指导以后的实现，并且属于下面之一时，才新建编号条目：

- 实质 ACP 翻译；
- 能力宣告；
- 原生 `sessionFile` 身份；
- 启动参数；
- 适配器与 Lody 的边界、所有权或集成顺序；详细归属只以 `MIGRATION.md` 为准，不在本仓库实现 Lody provider、runtime manifest、托管运行时解析、MCP 策略或 Lody 专用测试；
- 结算、用量、取消或子进程失败。

评审、调查、测试输出、测试运行、纯措辞、只改测试，都不建条目。拿不准就不写。

## 编号

用 `ls docs-ai | sort` 取下一个编号。取最大的三位数前缀再加 1，写成三位数。本 README 不是条目，不计入编号。尚无编号目录时，第一个合格条目是 `001`。不要回填。

## 生命周期

新目录名为 `NNN-<slug>`。其中：

- `000-plan.md`：实现前的计划
- `001-action.md`：对照代码写下实际做了什么
- `002-<topic>.md`：修订；同一目录里的新文件

该目录里的非编号文件以后可以是活 runbook，当它描述的过程变化时就地更新。编号文件不是活文档。

### 000 — 先写计划，核对后才实现

按下面的模板写 `000-plan.md`，状态先写「计划中」。背景、目标、非目标、方案、备选和验收证据是计划本身，不是事后补记。

「计划中」只起草，不改 `src/`。起草者不能把自己的计划标成「已核对」。人或另一个 agent 核对过目标、非目标、备选、难以回头的改动和验收证据，并明确允许实现之后，才把状态改为「已核对」，然后才能改 `src/`。核对者写在「规格核对」里。

### 001 — 实现后写行动

实现落地时写一次 `001-action.md`。记录现在有什么、哪里偏离了计划、哪些问题没有验证。然后把计划状态改为「已实现」。能一起提交就和代码改动一起提交。

一份计划分片交付时，每一片新增自己的 `002+` 文件。`001-action.md` 只在最后一片落地或条目被取代时写一次，并概括各片。

### 002+ — 新文件，不回写

后续是同一目录里的新文件：`002-<topic>.md`，然后下一个编号。不要回写已发布的编号文件。

已发布的 `000-plan.md` 只允许就地修改状态、「规格核对」，以及在「修订记录」末尾追加一行：

`- 更新于 YYYY-MM-DD：<一句> — 见 [002-<topic>.md](002-<topic>.md)`

不要就地修改背景、目标、方案、备选与决策，也不要就地修改已发布的 `001-action.md`。纠正写在新的修订文件里。

### 方向大改

如果改动替换了方案，而不是修补它，就新开一个编号。双向链接。旧计划状态写成「已被取代」，并给出指向新计划的相对链接。不要复用旧编号，也不要重写旧计划正文。

## 刷新索引

新增或重命名条目后，刷新本文件的索引。还没有条目时，索引保持下面那一行。以后每个条目一行：编号、指向该条目 `000-plan.md` 的链接、锚点日期、主题。只链接已经存在的路径。

## 写作规则

- 中文，可核对。计划通常 40–120 行，行动记录 30–100 行。时间线优先用表。
- 写出的每个仓库相对路径必须已经存在。本条目提议新建的文件必须标成提议，不能写成已经存在的链接。写之前先核对。不能核对的内容放进「未验证的问题」，不要在正文里当成事实。
- 没有实际跑过的构建、测试、smoke 或 contract，不能写成已通过。命令含义见 `AGENTS.md` 的「验证」。`npm run check`、`npm run build`、`npm pack --dry-run` 不需要 OMP，也不证明真实兼容。smoke 通过不是生产支持。`npm run contract` 仍是真实 OMP 和发布矩阵门禁：文档修改不要求跑它，它也不是可以忽略的检查。不要改写 `TESTING.md` 的 Required cases。
- `omp` 不在 `PATH` 上就停止。不要下载，也不要捆绑。CI 变绿不是矩阵通过。
- 只有 PR 确实存在时才写成 `#N`。
- 非目标只写本条目。不要把 `AGENTS.md` 的边界清单抄进每一份计划。
- 不要把 `docs-ai/` 或 `.omp/skills/` 加进 npm `files` 白名单。

## 模板

围栏里的块是模板，不是本仓库里的文件。

### 000-plan.md

```markdown
# NNN — <标题>：计划

| | |
| --- | --- |
| **状态** | 计划中 \| 已核对 \| 已实现 \| 已被取代，见 <相对链接> |
| **锚点日期** | YYYY-MM-DD |
| **规格核对** | 计划中写「未核对」。已核对必须写明核对者和「允许实现」。起草者不能核对自己的计划。 |
| **PR** | #N（只有 PR 存在后才填写） |
| **相关** | 已有根文档或同级条目；没有就省略 |

## 背景

问题；如果是修复，写观察到的症状。

## 目标

条目。

### 非目标

本条目正在决定的排除项。不要从 `AGENTS.md` 抄仓库边界。没有真实排除项就省略本节。

## 方案

打算怎么做。关键文件只有已经存在才能具名；新文件标成提议。

## 备选与决策

考虑过哪些方案，为什么选了这一个。记录决策，不只记录设计。

## 验收

用什么证据证明做对了。写出命令或观察方式。不要写还没跑过的结果。

## 修订记录

（在这里追加 `- 更新于 YYYY-MM-DD：... — 见 [00N-topic.md](00N-topic.md)`）
```

